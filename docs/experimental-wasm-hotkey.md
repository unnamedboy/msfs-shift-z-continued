# Experimental WASM Shift+Z

Branch: `experimental/wasm-hotkey`.

## No-toolbar startup candidate

The installed MSFS 2024 `Propdefs/1.0/Common/propingamepanels.xml` defines `managedByToolbar` (default true), `DependsOnToolBarAction`, `ShowOnEvent`, `headerVisible`, `noBackground`, and `isPanelCloseable` as panel registration properties. This experiment sets `managedByToolbar=false` and `DependsOnToolBarAction=false`, removes the toolbar button and header, and requests showing on `CHAIN_MESSAGE_FLIGHT_END_LOADING`. JS starts in the blank view; the first cycle shows flight data. This is a hypothesis based on the shipped property schema and the flight-loading event described in the [MSFS 2024 panel discussion](https://devsupport.flightsimulator.com/t/custom-made-panels-not-generated/13134). Schema support is not proof of automatic instantiation or event delivery for a standalone package in Free Flight. If it fails, examine the registration lifecycle before adding a bootstrap service or aircraft dependencies.

At the time of this first section no simulator test had been performed; the tests below have since confirmed automatic loading and the WASM hotkeys.

The existing FPS module maps `VK_LSHIFT+z` and `VK_RSHIFT+z` with `SimConnect_MapInputEventToClientEvent_EX1`. Private down/up client events are added to a notification group, both group priorities are set, and the input group is enabled explicitly. The down event sends `SHIFT_Z_CONTINUED_CYCLE` to JS through CommBus; a held-key latch suppresses repeat down events until key-up. JS subscribes to that event instead of DOM keydown. No existing simulator bindings are masked. Registration failures clear partial mappings and leave FPS operational; asynchronous SimConnect exceptions are logged.

## Configuration mode (2026-11-25)

Design: [config mode spec](superpowers/specs/2026-11-25-config-mode-design.md). The panel is registered at `defaultLeft=0`, `defaultTop=0`, `defaultWidth=178`, `defaultHeight=100`, `minHeight=100`, `resizeDirections=both` with `noBackground` and no close button; JS positions the text by percentage inside it. Panel sizes are percent of screen height, so 178 covers a 16:9 screen.

First sim test (2026-11-26, A310 at EDLW, 1920x1080): automatic loading, both hotkeys without focus, one step per press and click-through all passed; the Slew toggle never fired with that input profile. The panel was only a 54 px strip: without `resizeDirections` the game started the panel at `minHeight=5`, and the `ingame-ui` template (handled by the game) reports its own height back with `UPDATE_PANEL_HEIGHT`, so a 100%-height element kept the strip. `outline` was also not drawn; the configuration frame now uses `border`.

Retest (2026-11-26, after `resizeDirections=both`, `minHeight=100`, `defaultWidth=178`): the panel covers the screen; configuration card, drag to all edges, item and unit toggles, Reset position, Done, held keys and Alt+Tab all passed. Shift+Z pressed while the Esc pause menu is open is dropped, not delayed. Items and units were lost after Main Menu > new flight: the panel read its settings before the sim fired `dataStorageReady` (the `datastorage` object is attached only then), so it now reloads on that event unless the player already changed something in this flight. The text could also be dragged past the right edge; the drag now keeps the whole text box inside the panel.

Second retest (2026-11-26, ATR 72-600): items, units and position survive Main Menu > new flight and a full MSFS restart. At the right edge the text still stuck out: the absolute box shrinks to the space left (352 px in the centre, 328-342 px at the edge) and each move measured the shrunken box, so the limit crept outward. The limit now uses the larger of the box and its `scrollWidth`, and the widest size seen during the drag.

Third retest (2026-11-26, 787-10 at ENBR): right and bottom edges keep all text visible, Reset position and Done work. Each further drag at the right edge still narrowed the box by about 2 px. `#stats` now has `margin-right: -10000px` so the absolute box keeps its content width at the edge instead of shrinking (not yet tested in the sim). Purely vertical drags did not move the text in that test while diagonal ones did; the code handles vertical movement alone, so the next test should check this with real mouse input. The WASM module maps Shift+Z (cycle) and Ctrl+Shift+Z (configuration) for both Shift and Ctrl sides, each in upper and lower case, because the SDK's valid-key list uses `Z` while its example uses lower case. If `Z` and `z` both fire, the held-key latch absorbs the second down event.

## Conflict detection and key changes (2026-11-26)

Design: addendum in the [config mode spec](superpowers/specs/2026-11-25-config-mode-design.md). `key_conflicts.h` keeps the last 2048 simulator key events with frame numbers; a press is compared with events from 2 frames before to 10 frames after, minus events seen in the 60 frames before that. `hotkey_keys.h` parses the key set the panel sends. Both are header-only and tested on the desktop.

Fourth test (2026-11-26, A320neo v2, borrowed binding Ctrl+P = AUTOCOORD_TOGGLE): no false alarms over 5 presses during an auto start; key rules and refusal texts correct; right-edge drags kept a constant 576 px frame; a pure vertical drag works with absolute mouse moves (the test tool's relative moves were the cause). Failed: the panel's key set never reached WASM (no log line at all, while WASM to panel messages work), so the new key did nothing and the conflict prompt could not be shown. Keys pressed during capture also reach MSFS, Esc opened the MSFS pause menu instead of cancelling, and the hotkey press that ended a capture stepped the display afterwards.

Changes for the next test: the panel sends the key set over both `callWasm` (CommBus) and `callSimConnect`; the module also subscribes with `SimConnect_SubscribeToCommBusEvent`, logs `Key set received via ...` and answers `SHIFT_Z_CONTINUED_KEYS_STATUS`; the card shows `Key link: CommBus ..., SimConnect ...` with `applied`, `call failed: <error>` or `no reply`. The Change key button turns into Cancel, hotkey messages within 500 ms after a capture are ignored, and the card says the pressed keys also reach MSFS.

Fifth test (2026-11-26, A320neo v2 at EDLW): the module crashed at start, both in a flight and in the main menu after a restart. The console showed `mappings registered` and then, about 0.1 s later, `Module ... is now dirty`; `FPS module connected.` never appeared, so neither hotkey worked. The only new call between those two lines, compared with the fourth-test build that started fine, was `SimConnect_SubscribeToCommBusEvent`: calling it from a WASM module stops the module. The SimConnect path is removed. In its place the panel writes the key set as one number to `L:SHIFT_Z_CONTINUED_KEYS` (format in `src/wasm/hotkey_code.h`; a send counter makes every send a new value), and the module reads it each frame with `fsVarsLVarGet`, logs `Key L:var registered (id ..)` at start and answers with `via: lvar`. The card shows `Key link: CommBus ..., LVar ...`. With Shift+Z pressed while the module was dead, Slew still did not toggle and AUTO COORDINATION stayed off.

Fifth-test retest (2026-11-26, same aircraft): no crash, the module stays READY. The L:var path works: Ctrl+P was applied and cycles the display once per press. CommBus failed with an exception at `hotkeys.js` 42:32: Coherent GT has no `Array.prototype.flatMap`, so `hotkeySetText` threw before `callWasm` ran. That was also why the panel's keys never arrived in the fourth test. `comboDefinitions` now uses plain loops, and a test rejects `flat`/`flatMap` in the panel sources. Ctrl+P also ran AUTOCOORD_TOGGLE each time, but no conflict prompt appeared and the console showed nothing new; the module now logs a `Press check (...)` line with the count of new commands and of all key events seen, to tell whether the key event handler receives anything. Clicking Cancel did not end a capture, although the Altitude button worked at the same time. The cause is not known; the Change key/Cancel button now also acts on mousedown. During flight load the module once read the value 1 from the L:var and ignored it as invalid.

Sixth test (2026-11-26): `Key link: CommBus applied, LVar applied`; Cancel works with one click; Ctrl+P was applied through both paths. Still no conflict prompt: every press logged `Press check (...): 0 new command(s), 0 key events seen so far.`, so the key event handler registered in `module_init` received no event at all in the whole session, although Ctrl+P ran AUTOCOORD_TOGGLE each time. The documentation says the handler receives all key events, and a DevSupport thread reports the import fixed for standalone modules in 1.2.7.0. Next build: the handler is registered again on the SimConnect system events `SimStart` and `FlightLoaded` (the first registration happens in the main menu), and SimConnect watches AUTOCOORD_TOGGLE and SLEW_TOGGLE through a non-maskable notification group as a cross-check, logging `SimConnect saw ...`. If SimConnect sees the command and the handler still does not, conflict detection moves to SimConnect notifications.

Seventh test (2026-11-26): the handler was registered again on `SimStart` (Restart sends no `FlightLoaded`) and still saw 0 key events; SimConnect logged no `SimConnect saw ...` either, although Ctrl+P toggled AUTO COORDINATION three times and no SimConnect exception or "Command watch unavailable" line appeared. Our dispatch only handled `SIMCONNECT_RECV_ID_EVENT`; MSFS 2024 can deliver events as `SIMCONNECT_RECV_ID_EVENT_EX1` (five data words), which a DevSupport thread names as the reason notifications seemed missing. Next build: EX1 events are handled like plain events (the watch log says which form arrived), each unhandled SimConnect message type is logged once, and the two watched commands feed the conflict detector so the prompt and Ignore can be tested if they arrive.

Eighth test (2026-11-26): still no `SimConnect saw ...` line and 0 key events, no conflict card. Root cause on the SimConnect side: SimConnect event names differ from the `KEY_` names. Ctrl+P runs `KEY_AUTOCOORD_TOGGLE`, whose SimConnect name is `AUTORUDDER_TOGGLE`; the SimConnect event `AUTOCOORD_TOGGLE` is a different command (Y-axis inversion), so the watch was valid but never fired. After Restart the console also showed "Wasm: Trying to call Key Event Handler on dirty module" about once per second while both modules showed READY. Next build: the watch uses `AUTORUDDER_TOGGLE`, and the key event handler is no longer registered (it saw no event in three tests). If the "dirty module" lines disappear, they were about this module, and conflict detection stays on SimConnect notifications; a generic version then needs the SimConnect name of every command, not the `KEY_` names in `eventNames.js`.

Ninth test (2026-11-26): works. Every Ctrl+P logged `SimConnect saw AUTORUDDER_TOGGLE (EVENT)` (never EX1) and about 0.26 s later `Press check (cycle): 1 new command(s)`; the conflict card appeared after the first press. Ignore removed the warning and two more presses showed no card. The "dirty module" lines were gone (0 of about 10 000 messages, also after Restart), so they came from this module's `fsEventsRegisterKeyEventHandler` registration: in a standalone module the sim treats that handler as belonging to a dirty module and never calls it. Open points: the card shows the `KEY_` name (`AUTOCOORD_TOGGLE`) instead of the SimConnect name a player can search for; `SimConnect message type 2 not handled` is the harmless OPEN message; only two commands are watched so far. Limits for a generic watch: at most 1000 events per notification group and 20 groups per client.

Tenth build (generic watch): `tools/gen_watched_commands.py` reads the key event tables of the MSFS 2024 SDK documentation (first column, the SimConnect name) and writes `src/wasm/watched_commands.h`: 1576 of 2099 commands, leaving out `AXIS_*`, `*_SET`, `*_SET_*` and `DEBUG_*` (controllers and gauges send those continuously; key bindings do not run them). The module maps each to client event 100 + index in non-maskable groups 2 and 3 and feeds the index to the detector; the conflict message carries the names, so `eventNames.js` (KEY_ names) is gone. Unknown names come back as SimConnect exceptions: the first five are logged, the rest counted and shown on each `Press check` line. `RECV_ID_OPEN` is no longer logged as unhandled.

Tenth test (2026-11-26, A320neo v2): `Watching 1576 commands ... (0 calls failed)`, 168 SimConnect exceptions at the start screen (pairs of NAME_UNRECOGNIZED for the mapping and UNRECOGNIZED_ID for its group entry, so 84 documented names are unknown to the sim), no frame-rate change and no false report. Each Ctrl+P logged `Press check (cycle): {"key":"cycle","events":["AUTORUDDER_TOGGLE"]}`, but no card appeared: Ctrl+P had been ignored in the ninth test, and the ignore is kept for good, as designed. Three other bound combinations (Ctrl+N SPOILERS_OFF, Ctrl+2 AUTOPILOT_DISENGAGE_TOGGLE, Ctrl+V FLAPS_UP) logged no command at all. Likely cause: the watch groups had standard priority, so an aircraft that handles these commands itself and masks them in a higher-priority group hides them from this module. Next build: the watch groups use `SIMCONNECT_GROUP_PRIORITY_HIGHEST` (non-maskable, so the module still masks nothing), and each unknown name is logged as `Unknown command name ...` (the module keeps the packet id of each mapping) so the generator can leave those names out. Ignore now turns off all conflict warnings (any key), as the user intended; the old per-combination list is dropped, so the ignored Ctrl+P from the ninth test no longer applies.

Eleventh test (2026-11-26, A320neo v2): passed. With the watch groups at the highest priority, Ctrl+N, Ctrl+V, Ctrl+2 and Ctrl+P each opened the card within 0.3 s, naming SPOILERS_OFF, FLAPS_UP, AUTOPILOT_DISENGAGE_TOGGLE and AUTORUDDER_TOGGLE (long names wrap inside the card). After Ignore, a Ctrl+N press was still logged but opened no card; Ctrl+Shift+Z gave no false report; no frame-rate change. The sim rejected 84 documented names (among them AUTOCOORD_TOGGLE, AUTOCOORD_ON/OFF, FLAPS_4 and AP_MASTER_ALT); they are listed in `tools/unknown_commands.txt`, which the generator now leaves out, so the module watches 1492 commands.

Twelfth test (2026-11-26, A320neo v2): passed. `Watching 1492 commands for key conflicts (0 calls failed).` with no `Unknown command name` or exception line (`0 SimConnect exceptions so far`); the settings card no longer shows the key path line when the keys arrive; with Ignore set, Ctrl+P logged AUTORUDDER_TOGGLE and opened no card; no frame-rate change.

Known limits: the detector keeps the last 2048 watched events, so an aircraft that fires watched commands in large bursts could push the baseline out of the buffer and cause a false report; the warning uses SimConnect names, which may differ from the names in the MSFS controls; the panel width (178% of the screen height) covers 16:9 only, so on ultrawide screens the text may not reach the right edge; if Frame and PauseFrame both fire while paused, the detector counts frames twice and its window halves during a pause (not checked in the sim); Ignore turns off all conflict warnings for good (the user's choice) and cannot be undone from the card.

### Still to check in the sim

1. False reports over a longer flight in other aircraft (the tests so far used the A320neo v2 parked or on the ground).
2. An ultrawide screen: whether the text reaches the right edge.
3. Active pause: whether Frame and PauseFrame both arrive, and whether a conflict pressed while paused is still reported.
4. The key path line on the settings card when neither path delivers the keys (only covered by the desktop tests).

## Validation in MSFS 2024 (first to third tests, passed except where noted above)

1. Build and install the package, restart the simulator, and enter a flight without opening any toolbar panel. Press Shift+Z: line 1 must appear at the top left. If nothing appears, distinguish failure to load the JS panel from failure to receive WASM input. Check the WASM console for `Shift+Z and Ctrl+Shift+Z mappings registered` and any SimConnect exceptions (an invalid key string shows up as an exception, not a failed call).
2. Click the cockpit or outside view so the panel has no keyboard focus. Press left Shift+Z three times: line 1 -> both lines -> off. Repeat with right Shift. Each press must advance exactly once (no double steps from the `Z`/`z` mappings).
3. With the text showing, click cockpit switches that lie under and around the text and in the rest of the screen: every click must reach the cockpit. Also check the panel does not dim or tint the view.
4. Press Ctrl+Shift+Z: the settings card appears in the screen centre and the text shows both lines with a dashed outline. The view must not advance as a side effect. Try all four Ctrl/Shift side combinations.
5. Drag the text to each screen edge: it must reach close to all four edges (this shows whether the panel really covers the full screen; if it stops short, record where). Toggle several items and both unit buttons; check `ALT: ... M MSL` and `KM/H IAS`. Press Reset position, then Done.
6. Hold Shift+Z and Ctrl+Shift+Z: no repeats. Test releasing Z first, Shift first, and Alt+Tab while held; ensure no stuck latch.
7. Verify FPS updates while cycling. Pause, press the shortcuts, and resume: record delayed delivery.
8. Return to the main menu, start another flight, and check that position, items and units were kept and the overlay starts off. Restart the simulator and check again.
9. If the panel still does not cover the screen, first check whether the game restored the size saved from an earlier test (toolbar settings > Reset Panels), then try a build with a `<Preset PanelLayout="FULL_SCREEN"/>` child (a property listed in the shipped `propingamepanels.xml`).
